1. Overview

Based Moer combines the Moerverse pixel-art IP with Moer AI, NFT-gated experiences, education, games and Base-native infrastructure. The project is designed as one connected ecosystem rather than a collection of unrelated tools.

Core architecture: Moer owns the intelligence, strategy, safety rules, product experience and identity. Base provides secure onchain account, permission and execution infrastructure underneath it wherever technically sensible.

3. Moer Intelligence

Scanner

Moer Scanner remains the project’s proprietary decision engine. External wallet, Base or Coinbase tooling must not replace its strategy version, confidence thresholds, setup validity, signal lifecycle or risk logic.

Token Radar

Radar discovers and studies assets using market, liquidity, security, holder and Base-native observations. New research inputs cannot affect production score simply because they look interesting.

collect → measure → fixed-horizon forward test → qualification → time-split out-of-sample validation → human review → explicit scoring change

Current research families include DEX/liquidity state, holder/concentration changes, aggregate ERC-20 transfer flow and Flashblocks market context. All remain zero-weight until proven and separately approved.

4. Moer Agent

Moer Agent is the controlled action layer. The intended flow is:

Moer Scanner decision → Moer risk policy → user permission check → managed operator policy → reviewed execution adapter → Base

AgentKit/CDP may provide execution plumbing. They do not become Moer’s trading brain. Generic arbitrary transfer, swap or deployment actions are intentionally excluded from the production design.

6. Safety Architecture

  • Live-fund execution remains disabled before testnet.
  • Execution spender starts paused and is Base-chain locked.
  • Single-spend limits and approved routes/assets are enforced.
  • Emergency permission revocation and permanent disable paths exist.
  • Raw operator private keys are prohibited by the managed-operator design.
  • Foundry, Python invariants and Slither are part of the pre-testnet gate.
  • Radar research features cannot silently write production scores.
Passing compilation or backtests does not grant deployment permission. Deployment is a separate release state.

7. Testnet Plan

Base Sepolia is the project’s full-system rehearsal before public launch. The planned sequence is:

  1. Run final website/API/security release audit.
  2. Confirm Base Sepolia infrastructure and test assets.
  3. Deploy the testnet-only execution spender after explicit approval.
  4. Create/review bounded test permission.
  5. Quote and simulate the approved route.
  6. Execute with test assets only.
  7. Verify output receipt and lifecycle tracking.
  8. Test reverse path where supported.
  9. Revoke permission and confirm the revoked state.
  10. Run failure/negative controls and document results.

No mainnet transition occurs automatically after a successful Sepolia test.

9. Project Principles

  • Pixel first: technology supports the art and Moerverse rather than replacing it.
  • Moer decides: proprietary intelligence remains the decision authority.
  • Prove before weighting: research does not become production logic without evidence.
  • Permission before execution: users retain explicit, bounded authorization control.
  • Fail closed: missing providers, mismatched accounts or unsafe states stop the action.
  • Testnet before launch: public rollout follows a complete rehearsal, not the other way around.
