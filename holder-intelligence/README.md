# Holder watch room — isolated research page

This new `/holder-intelligence/` page uses the existing portal header/wallet helpers and the separately audited holder client/session modules. Existing production routes, navigation, authentication and styles are unchanged. Its reviewed release configuration is disabled by default, with no backend origin or markets specified. Query strings, wallet preferences and local storage cannot enable it. No fabricated records appear.

The page supports explicit holder login, creating a price watch with a caller-chosen idempotency key, reading/cancelling a known watch ID, listing/paging in-app notices and reading/acknowledging a known notice ID. Current API contracts do not include watch listing. IDs returned after creation are shown in the form; they are cleared with the private views on wallet authority changes. Copy a watch ID yourself if you need to retrieve it after reconnecting; the page persists no watch IDs or session tokens.

A future release must supply `release-config.js` from trusted application code with `enabled: true`, one HTTPS `apiOrigin`, its exact `approvedApiOrigins` allowlist and server-owned `allowedPairs`. The same reviewed origin must expose compatible login and intelligence routes and share session verification. The previous dedicated read-only staging factory had no login routes; a page pointed at it cannot log in. The newer opt-in local staging login bridge needs its own reviewed configuration. No automatic fallback to the production Agent login is implemented. The legacy production `/v1/agent/auth/challenge` and `/verify` write challenge/session/account/login records; merely enabling this page against production would authorize those calls, so production mounting remains a separate release action.

`bootstrap.js` chooses the source-aware wallet provider through `wallet-auth.js` on the explicit login gesture, then signs with that exact provider. Base Account signs the hex-encoded message; injected wallets sign the plain login text. The controller binds `accountsChanged`, `chainChanged` and `disconnect` directly to the chosen signer before reading chain/accounts. It checks live Base chain `0x2105` and matching accounts before login, immediately before signing and immediately after signing. Protected watch/inbox actions recheck that same live provider chain/account immediately before dispatch and before rendering the response; a silent change without an event revokes authority and blocks the request or its result. A provider without subscription/removal support is rejected. Selecting a replacement provider detaches old listeners, and queued old-provider events cannot revoke its session. Provider changes immediately invalidate authentication, cancel client requests and clear private views; no reload is required. This avoids relying on legacy header reload handlers or a differently instantiated Base Account provider.

The page's DOM controller only renders validated allowlisted response schemas via `textContent` and created elements. Unknown fields, enabled trading/external-delivery flags, mismatched IDs, unsupported native markets, invalid observation chronology, mismatched completion identity/condition, malformed timestamps and invalid notification states fail closed. Response transport byte caps/deadlines remain in the underlying client/session; a separate 60-second page operation deadline covers provider preparation (optionally 1–120000 milliseconds via reviewed config). A late wallet result cannot regain authority. Detached old inbox controls cannot render records into a replacement session.

No production page loads these new files. No actual signatures, production API writes, external delivery, hosted holder journey or smart-account login compatibility were tested by the DOM tests. Run `node --test tests/holder_intelligence_page.test.cjs` or the complete `node --test tests/*.test.cjs` suite. Test fixtures inject providers, sessions and responses; the separate root-led TCP journey validates actual client/backend HTTP behavior. A real connected-holder browser check remains a release gate.

## Pilot audience configuration

The enabled pilot page refuses missing, empty, unknown or legacy proof versions; generic session legacy compatibility is not a page fallback. The checked-in configuration explicitly requests `loginProofVersion: 'moer-staging-eoa-v1'` while retaining `enabled: false`, `apiOrigin: null` and `audience: null`. To prepare a reviewed pilot acceptance deployment, configure an approved HTTPS API origin and set the trusted `audience` to exactly that canonical origin. Never derive it from `location`, a challenge response or storage, and never configure the legacy proof as a pilot fallback. `page.js` passes these fields directly to the session coordinator; it does not guess them.

The backend's versioned `Moe AI Staging Login v1` template, `issued_at` and proof/audience echoes must match the coordinator contract described in `HOLDER_INTELLIGENCE_CLIENT.md`. The unchanged production legacy client option exists for explicit legacy integrations, not pilot audience binding. The reviewed pilot must use its isolated local session bridge. Hosted configuration is still disabled, so these changes alone do not perform a holder login or write state.

## Moe AI evidence review slice

The page includes a deterministic review form for 1–8 authorized record references, one `product record_id` per line. Supported products are `scanner`, `radar_signal` and `radar_candidate`. It displays supplied-record coverage, facts, literal source citations/timestamps, abstention/missingness and source limitations. A complete review describes explainability of those records only. It supplies no market-wide ranking, calibrated probability or trade authorization and saves no conversation memory.

The client request remains bound to the current holder session and live chosen provider. Disconnect/access denial clears the form and results; stale responses cannot render across wallet replacement. The page remains disabled until the same reviewed scoped-auth API is configured. The new `/v1/intelligence/review` route must be available in that isolated application; there is no production fallback or added model provider.

New module tests validate Scanner/Radar results, unknown/missing records, exact request binding, coverage integrity, citation chronology, schema/byte limits and text-only rendering. The page tests include current-session denial and disconnect while a review is pending. Synthetic fixtures in tests are clearly labeled and do not appear in the shipped page.

## Discover references before reviewing

Holders can explicitly load up to 20 recent source-row references for Scanner, Radar signals or Radar candidates. Each row shows its exact product/record ID, any source display label and any stored row timestamp, with evidence not evaluated. Labels do not establish native identity; row timestamps do not establish provider observation or freshness. Loading a list does not trigger a review automatically.

Checkbox selection fills the existing manual reference form. Up to eight exact references can be selected, preserving valid manual references across products. Source lists and selections clear on authority loss, and controls from an older listing cannot change the new one. The list remains authenticated approved shared-holder data, not private account discovery, free-text search or opportunity ranking. Unknown/malformed responses fail closed. The disabled release configuration and scoped pilot login remain unchanged.
